### 🟠 Roadmap omits required Phase 2 and Phase 6 deliverables

`docs/roadmap.md:17` · category: correctness · confidence: 98

**Problem**: The Phase 2 checklist omits the minimal local app shell and diagnostics surface required by PRD Phase 2, while the Phase 6 checklist omits incremental monitoring of new sessions.

**Why it matters**: Implementing directly from this roadmap can complete Phase 2 without the required shell and Phase 6 without monitoring, leaving explicit PRD and traceability requirements unmet while making the phase exit report claim complete scope.

**Suggested fix**: Add a Phase 2 item for the minimal diagnostics shell (source/layout, import progress and counts, warnings, and unavailable-usage counts) and a Phase 6 item for low-overhead incremental session monitoring.

**Evidence**: docs/roadmap.md:17-35 and 58-62 omit both deliverables; PRD.md:532-543 requires the Phase 2 app shell and Phase 6 incremental monitoring; docs/requirements-traceability.md:429 and 433 assign them; docs/phase-1-audit.md:584-587 explicitly scopes the Phase 2 shell.

### 🟠 Provider and model open question is closed without identifying either

`docs/requirements-traceability.md:457` · category: correctness · confidence: 96

**Problem**: PRD-OPEN-002 is marked Complete even though its note only states that 45 distinct model values exist; it identifies no provider or model and records no runtime-discovery default for the unresolved identities.

**Why it matters**: The Phase 4 pricing catalogue and provider/model mapping depend on these identities, so falsely closing this Phase 1 question can leave model-to-provider mappings incomplete or incorrectly grouped and makes the audit's claim to resolve all open questions unreliable.

**Suggested fix**: List the provider and model identities found by the aggregate-only audit, or keep this row Not started and record the unresolved evidence together with the safe default that Phase 2 discovers and reports the identities at runtime.

**Evidence**: docs/requirements-traceability.md:457 says only `45 distinct model values are present`; PRD.md:552-554 asks which providers/models are used; docs/phase-1-audit.md:476-480 repeats the count rather than the identities.

### 🟠 GET allowlist is attached to the wrong API layer

`docs/system_diagram.md:42` · category: correctness · confidence: 93

**Problem**: The diagram attaches `GET allowlist` to Observatory's local API layer, although ADR-003 scopes that allowlist to an optional supplement for the OpenCode HTTP API and ADR-009 explicitly expects state-changing local routes.

**Why it matters**: Read literally, the planned API cannot support the required POST-style user actions such as requesting AI processing or resetting derived data; alternatively, implementers may mistake the boundary as applying to the wrong API and weaken or misplace the OpenCode API restriction.

**Suggested fix**: Label the local API as loopback-only with Host and Origin checks, and show the OpenCode HTTP API as a separate optional supplement reached only through the explicit GET allowlist.

**Evidence**: docs/system_diagram.md:42 places `GET allowlist` in `Local API layer`, while docs/system_diagram.md:68-70 and docs/architecture-decision-record.md:186-190 tie the allowlist to the OpenCode HTTP API; docs/architecture-decision-record.md:526-528 requires Origin checks on state-changing local routes.
